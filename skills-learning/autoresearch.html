Autoresearch

自动研究分析任务 · 深入调研技术方案输出完整报告

🔬 什么是 Autoresearch？

Autoresearch 是一种自动化的研究分析技能。当面对需要深入调研的技术问题时，它能够自主搜集信息、分析对比、权衡利弊，最终输出完整的研究报告。

🌰 典型场景

用户问："我们项目应该用 Redis 还是 Memcached 做缓存？"

→ Autoresearch 自动：

1. 搜集两种方案的技术特性

2. 对比性能、功能、成本

3. 分析适用场景

4. 结合项目实际给出建议

🎯 触发条件

以下情况适合使用 Autoresearch：

  • 技术选型问题（数据库、框架、工具）
  • 需要对比多个方案
  • 调研新技术的适用性
  • 评估迁移成本和风险
  • 用户问"应该用 X 还是 Y"
💡 区分

如果是"实现某个功能"，用普通 Agent；如果是"搞清楚某个问题"，用 Autoresearch。

📋 研究流程

Autoresearch 按照结构化的流程进行研究：

/**
 * Autoresearch 研究流程
 */

// Phase 1: 明确研究目标
明确：
- 需要解答的核心问题是什么
- 研究的边界和约束
- 期望的输出形式

// Phase 2: 信息搜集
搜集渠道：
- 官方文档
- 技术博客/论文
- 开源项目实践
- 社区讨论

// Phase 3: 分析整理
分析维度：
- 技术特性对比
- 性能基准数据
- 社区生态
- 学习曲线
- 维护成本

// Phase 4: 综合判断
权衡因素：
- 当前团队能力
- 项目规模和时间
- 长期维护预期
- 社区活跃度

// Phase 5: 输出报告
报告结构：
- 执行摘要
- 方案对比
- 适用场景
- 推荐建议
- 参考资料

📊 分析框架

使用结构化的框架进行分析：

/**
 * 多维度分析框架
 */
const ANALYSIS_FRAMEWORK = {
  dimensions: [
    {
      name: '功能完整性',
      weight: 0.2,
      criteria: ['核心功能', '扩展能力', '插件生态']
    },
    {
      name: '性能表现',
      weight: 0.25,
      criteria: ['响应延迟', '吞吐量', '资源消耗']
    },
    {
      name: '易用性',
      weight: 0.15,
      criteria: ['学习曲线', '开发体验', '文档质量']
    },
    {
      name: '可维护性',
      weight: 0.2,
      criteria: ['社区活跃度', '更新频率', '技术支持']
    },
    {
      name: '成本考量',
      weight: 0.2,
      criteria: ['License费用', '运维成本', '人力成本']
    }
  ],

  // 综合评分
  score: (scores) => {
    return scores.reduce((sum, s, i) =>
      sum + s * ANALYSIS_FRAMEWORK.dimensions[i].weight, 0
    );
  }
};

📝 输出报告示例

针对"Redis vs Memcached"的完整报告：

# 缓存方案技术调研报告

## 执行摘要
综合对比 Redis 和 Memcached，考虑项目需求，
**推荐使用 Redis**。

## 方案对比

| 维度 | Redis | Memcached |
|------|-------|----------|
| 数据类型 | String/Hash/List/Set | 仅 String |
| 持久化 | 支持 RDB/AOF | 不支持 |
| 集群 | 原生支持 | 需要客户端实现 |
| 性能 | 略低（功能更多） | 略高（简单） |
| 文档 | 完善 | 简洁 |

## 详细分析

### 功能对比
- Redis 支持更丰富的数据结构
- Memcached 专注于简单缓存场景

### 性能基准
- 纯 Get/Set 场景：Memcached QPS 高约 15%
- 复杂操作场景：Redis 整体更优

### 生态对比
- Redis 社区更活跃，版本迭代快
- Memcached 维护稳定但更新较慢

## 适用场景

### 适合 Redis
- 需要复杂数据结构
- 需要持久化或主从复制
- 分布式缓存场景
- 消息队列、排行榜等场景

### 适合 Memcached
- 简单的 Session 缓存
- 追求极致性能
- 不需要数据持久化

## 推荐建议

基于项目需求（需要 Session + 用户画像缓存）：
**选择 Redis**
- 功能覆盖全面
- 运维成本可控
- 团队已有 Redis 经验

### 实施建议
1. 先部署单节点 Redis
2. 监控性能和资源使用
3. 根据需要扩展为集群

---
*调研时间：2026-04-28*
*参考资料：Redis 官方文档、Memcached Wiki、性能基准测试报告*

💡 研究技巧

  • 多源验证：单一来源可能被误导，多方印证更可靠
  • 时间筛选：技术文章有时效性，优先看近两年的
  • 实践优先：GitHub 真实项目比理论更可信
  • 边界明确：清晰界定适用范围，避免以偏概全
  • 量化对比：能数字化的不模糊，用数据说话
