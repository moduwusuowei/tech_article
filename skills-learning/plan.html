Plan

战略规划与需求分析，从模糊到清晰

📋 什么是 Plan

Plan 是一个战略规划技能。它的核心作用是把模糊的需求变成清晰可执行的计划。

Plan 有多种模式：交互式访谈（Interview）、直接规划（Direct）、共识规划（Consensus）、计划审查（Review）。根据任务复杂度选择合适的模式。

📋 四种模式

  • Interview（默认）：交互式提问，逐步澄清需求
  • Direct：直接生成计划，适合需求已清晰的情况
  • Consensus：多方评审达成共识，适合高风险决策
  • Review：审查现有计划的质量

📋 使用场景

  • 模糊需求："我想做个 todo 应用" → 澄清：目标用户、平台、核心功能
  • 大型重构：规划迁移步骤、风险点、回滚方案
  • 技术选型：评估多个方案的优劣，做出决策
  • PRD 生成：为新功能编写完整的产品需求文档
  • 计划审查：检查现有计划是否完整、可行
🌰 场景示例：开发新功能

用户说："plan 开发一个聊天功能"

Plan 进入 Interview 模式：

Q1: "这个聊天功能是私聊还是群聊？"

A1: "主要是私聊"

Q2: "需要支持文件传输吗？"

A2: "先只需要文字和图片"

... 逐步澄清后生成完整计划

⌨️ 命令格式

基础命令：

plan "开发聊天功能"

直接模式（跳过访谈）：

plan --direct "添加缓存功能"

共识模式（多方评审）：

plan --consensus "重构认证模块"

审查模式：

plan --review ".omc/plans/xxx.md"

⚙️ 工作原理

Plan 会生成标准化的计划文件：

  • Requirements Summary：需求概要
  • Acceptance Criteria：验收标准（可测试）
  • Implementation Steps：实现步骤（含文件引用）
  • Risks and Mitigations：风险和缓解措施
  • Verification Steps：验证步骤
  • ADR（Consensus 模式）：决策记录
💡 输出位置

计划文件保存在 .omc/plans/ 目录，可供后续的 ralph、team 等技能使用。

🤝 Consensus 模式详解

共识规划会经过三轮评审：

  • Planner：生成初稿计划
  • Architect：架构评审，寻找设计缺陷
  • Critic：质量评审，检查遗漏和风险

如果 Critic 拒绝，会返回 Planner 修订，最多 5 轮迭代，直到达成共识。

💡 何时用 Consensus

高风险决策：认证/安全模块、数据迁移、破坏性变更、公有 API 变更。

⚠️ 注意事项

  • 不是编码：Plan 只规划，不写代码
  • 迭代提问：一次只问一个问题，让回答深入
  • 90%+ 可测试：验收标准必须具体可验证
  • 80%+ 引用：计划中 80% 以上的声明要有文件/行号引用
⚠️ 不要用 Plan 的场景

简单明确的任务（直接说"写一个 hello world"）| 只需要问一个问题的情况
